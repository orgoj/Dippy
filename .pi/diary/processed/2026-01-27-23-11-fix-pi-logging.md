## Task Summary
The user noticed "suspicious" behavior in the `pi` extension (transforming `read` to `cat`) and missing entries in `audit.log`. The goal was to investigate the extension behavior, fix the missing logging in `pi_wrapper.py`, and add agent identification (`agent` field) to the audit logs to distinguish between Claude, Pi, and CLI usage.

## Work Done
- **Analyzed Extension Behavior**: Confirmed `dippy-extension.ts` is correct. The observed `read_file() { cat ... }` pattern was an optimization generated by the `pi` agent itself, not the extension.
- **Fixed Missing Logging**: Discovered `pi_wrapper.py` was not calling `log_decision`. Added logging logic to capture `bash`, `read`, and `edit` operations from `pi`.
- **Added Agent Identification**:
  - Modified `log_decision` in `src/dippy/core/config.py` to accept an `agent` parameter.
  - Updated `src/dippy/pi_wrapper.py` to pass `agent="pi"`.
  - Updated `src/dippy/dippy.py` to pass `agent=MODE` (claude, gemini, cursor, cli).
- **Fixed Style Violations**: Replaced banned `import shlex` in `config.py` with `dippy.core.parser.tokenize`.
- **Verified & Polished**:
  - Ran `just fmt --fix` to resolve formatting issues.
  - Ran `just check` (11017 tests passed).
- **Documentation**: Updated `CHANGELOG.md` and `README.md` with new features.
- **Commit**: Committed changes with a descriptive message.

## Design Decisions
- **Agent Field in Logs**: Added `agent` as a top-level field in the JSON log entry. This allows easy filtering and analysis of which agent (or user via CLI) performed an action, which is crucial as the ecosystem grows (Claude, Pi, Gemini).
- **Using `dippy.core.parser.tokenize`**: The project bans `shlex` (to avoid dependency issues or ensure consistent parsing behavior via `Parable`). When I encountered the style error, I switched to the project's internal tokenization utility.

## Mistakes & Corrections

### Where I Made Errors:
- I initially missed that `pi_wrapper.py` wasn't logging at all until the user pointed out the empty logs. I assumed it shared the logging logic with `dippy.py` more closely than it actually did.

### What Caused the Mistakes:
- **Assumption**: I assumed the wrapper was a thin layer over `dippy.py`'s main logic, but it actually imports `analyzer` directly and handles its own output/logging (or failed to handle it).

## Lessons Learned

### Technical Lessons:
- **Wrapper Isolation**: `pi_wrapper.py` is a standalone entry point. Any global behavior added to `dippy.py` (like logging or mode detection) must be manually replicated or shared in `config.py`/`analyzer.py` if intended for `pi` as well.
- **Style Enforcements**: The `check-style` script is strict about imports. Always check existing patterns or `tools/check_style.py` output before introducing standard library modules like `shlex`.

### Process Lessons:
- **Verify Logs**: When debugging "why isn't X showing up", check the entry point code first to see if it even *tries* to log.

### To Remember for CLAUDE.md:
- `pi_wrapper.py` needs manual updates when core logging logic changes.
- `just check` is mandatory before commits to catch banned imports.
