## Design Decisions

### Rotation Timing and Trigger
- **Decision**: Rotate on first Dippy run after midnight, not before every write
- **Rationale**: User explicitly corrected initial approach - checking rotation on every write is unnecessary overhead. Once per day (at config load) is sufficient.

### Rotated File Naming
- **Decision**: Use yesterday's date in filename: `audit-YYYY-MM-DD.log`
- **Rationale**: Today's logs always go to `audit.log` (active file). Tomorrow's first run rotates today's log to yesterday's date. This prevents rotating on every startup.

### Rotation Check Logic
- **Decision**: Check if yesterday's rotated file already exists to detect if rotation happened today
- **Rationale**: Simple file existence check is reliable - if `audit-2026-01-17.log` exists (and today is 2026-01-18), we already rotated today.

### Cleanup Strategy
- **Decision**: Only clean up old logs when rotation happens, not on every run
- **Rationale**: User emphasized this is a KISS feature - don't add overhead checking for old files on every startup.

### Configuration Placement
- **Decision**: Add `log_rotate_max_days` as integer setting with default of 30 days
- **Rationale**: Simple, clear, follows existing config pattern. Set to 0 to disable rotation.

## Lessons Learned

### Technical Lessons:

1. **Python datetime for date calculations**: Use `datetime.now() - timedelta(days=1)` for yesterday's date
2. **Path stem parsing**: `old_log.stem.split("-")[1:4]` extracts YYYY-MM-DD from `audit-YYYY-MM-DD.log`
3. **File existence check**: Simple `rotated_path.exists()` is sufficient to detect if rotation already happened today
4. **String date comparison**: Works directly with ISO format: `"2026-01-17" < "2026-01-18"`
